# GitHub 기반 AI 캘린더 갱신안

[English](../en/calendar-automation.md) · [콘텐츠 모델](content-model.md) · [속도 기준](design-quality.md)

**사용자 확정:** GitHub를 콘텐츠 원본으로 사용하며, 초기에는 이 작업의 정기 점검으로 AI 판단과 갱신을 수행합니다. 매일 오전 9시 America/New_York 기준으로 돌아오는 정기 작업을 설정했습니다. 별도 GPT API와 자동 병합은 활성화하지 않았습니다. 실제 도감 구현 전에는 검증된 조사 자료만 정리합니다.

## 1. 실행 방식

| 방식 | 동작 | 조건 |
| --- | --- | --- |
| 현재 작업의 정기 점검 · 선택됨 | 이 작업이 같은 프로젝트 맥락으로 재실행되어 출처 확인·판단·GitHub 갱신 | 로컬 프로젝트 접근에는 PC와 앱 실행이 필요하며 계정 사용 한도·도구 접근의 영향을 받음 |
| GitHub Actions + GPT API · 추후 전환 후보 | GitHub 실행 환경이 공지를 확인하고 API로 판단한 변경안을 PR에 저장 | API 키·사용료, 실행 한도와 실패 처리 필요; 개인 PC 전원에 독립적 |

GitHub 실행 환경은 [GitHub-hosted runners](https://docs.github.com/en/actions/concepts/runners/github-hosted-runners), 로컬 정기 실행 조건은 [OpenAI 정기 작업 문서](https://learn.chatgpt.com/docs/automations?surface=app)에 근거합니다. 정기 작업은 이 작업에 연결되며 앱 관리 ID는 `automation`입니다. API 방식은 미구현 대안입니다.

## 2. 하나의 공통 갱신 절차

1. 공식 중국·글로벌·한국어 공지를 확인하고 새로운 자료 또는 실질적인 변경만 선별합니다. 수집 실패는 ‘업데이트 없음’과 구분합니다.
2. 원문 날짜·서버·외관·획득 방식·명칭을 구조화합니다. 이미지 공지를 판독하지 못하면 미확인으로 남깁니다.
3. 검증된 중국/글로벌 대응 기록과 현재 예상을 입력으로 제공합니다. 대화 기억이나 모델의 내장 지식만으로 일정을 생성하지 않습니다.
4. AI는 유지·추가·수정·철회 중 제안을 만들고 예상 범위, 근거, 반대 증거, 영어·한국어 설명을 출력합니다. 정보 부족일 때는 미정을 반환할 수 있어야 합니다.
5. 별도 검증기가 출처 연결, 날짜 정밀도, 서버 범위, 번역, 중복 ID, 기존 공식 기록 훼손 여부를 확인합니다. 형식 검증 통과가 사실 확인을 대신하지 않습니다.
6. 실제 변경이 있으면 영어 PR을 생성하거나 기존 갱신 PR에 반영합니다. 이전 예상을 보존하고 변경 사유를 기록합니다. 변화가 없으면 PR을 만들지 않습니다.
7. 초기 게시 흐름은 검토 후 병합·배포입니다. 자동 병합은 선택된 정책이 아니며 별도 요청 전까지 켜지 않습니다. AI의 근거 평가는 공식 확정 배지를 만들지 않습니다.
8. 콘텐츠 업데이트를 완료할 때마다 [릴리스 절차](releasing.md)에 따라 버전과 영어·한국어 노트를 갖춘 GitHub 릴리스를 발행합니다. 변경 없는 점검은 버전을 올리거나 릴리스를 만들지 않으며, 열린 PR은 완료된 릴리스가 아닙니다.

[Responses API 웹 검색](https://developers.openai.com/api/docs/guides/tools-web-search)은 조사 도메인 제한과 출처 목록을 지원합니다. 이를 활용하되 가져온 원문을 확인하는 절차를 둡니다. [Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs)는 결과 형식을 맞추는 데 사용하며 내용의 진실성을 보장하는 수단으로 취급하지 않습니다.

## 3. 판단 기록

각 제안에는 외관 ID, 이전/제안된 예상, `precision`, 적용 서버·지역, 출처 ID와 확인 시각, 비교 사례, `evidence_strength`, 영어·한국어 이유, 전제, 다음 검토일, 실제 사용 모델/프롬프트 버전, 기존 예상을 대체하는 관계를 남깁니다.

같은 출처와 입력으로 반복 실행해도 중복 PR이나 일정 흔들림을 만들지 않습니다. 명확한 새로운 근거가 없으면 이전 판단을 유지합니다. 과거 결과를 지우지 않아 추후 실제 글로벌 출시와 비교할 수 있어야 합니다.

## 4. 제안 주기와 실패 처리

- 공지 확인은 매일 오전 9시 America/New_York에 하루 1회 실행하도록 설정했습니다. 새 공지가 있으면 관련 외관만 재검토합니다. 서머타임을 포함한 실제 다음 실행 시각은 앱의 예약 표시를 기준으로 확인합니다.
- 주 1회 예상 목록 전체의 검토 기한과 실제 결과를 점검합니다. 모델 호출은 변경·기한 경과 항목으로 한정합니다.
- GitHub 정기 실행은 지연될 수 있으므로 실시간 보장을 하지 않습니다. 수동 실행 경로와 마지막 성공 확인 시각을 둡니다. [GitHub 실행 이벤트](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows)
- API·수집 실패 시 마지막 정상 데이터를 유지하고 실패 원인·재시도 상태를 기록합니다. 오류, 중요한 변경, 사용자 조치 필요 시에만 알립니다.
- 공식 날짜가 도래했다는 이유만으로 실제 출시 확인을 생략하지 않습니다. 만료된 예상은 재검토 대상으로 표시합니다.

## 5. 비용·접근·사이트 속도

API 키는 GitHub의 비밀 설정에 두고 브라우저나 저장소 파일에 포함하지 않습니다. 처리할 공지 수·입출력 길이·재시도 횟수·동시 실행을 제한하고 사용량을 기록합니다. 실제 비용은 선택 모델·검색·이미지 입력량에 따라 달라지므로 작은 자료 묶음으로 측정한 뒤 운영 주기를 정합니다. [API 요금](https://developers.openai.com/api/docs/pricing)

AI에 원문을 자료로 제공하되 원문에 포함된 지시를 실행 명령으로 취급하지 않습니다. 생성된 변경은 콘텐츠 경로에 한정하고 실행 코드·설정 변경과 분리합니다.

캘린더를 여는 방문자는 GPT 응답을 기다리지 않습니다. 갱신 작업이 끝난 검증 데이터로 페이지를 생성·캐시하고, 도감·상세·캘린더가 같은 데이터를 읽습니다. 따라서 AI 작업 지연이나 실패가 화면 탐색을 멈추지 않습니다.

## 6. 현재 상태와 다음 완료 기준

정기 점검을 설정하기 전에 중국·글로벌·한국어 공식 소식 목록의 접근과 기존 출처 목록을 수동으로 재확인했습니다. 이는 출처 접근 점검이며 이미지 판독·실제 예측·캘린더 게시 전체 흐름을 시험한 것은 아닙니다.

기존 매일 점검은 실제 JSON 콘텐츠와 검증 명령을 사용합니다. 9월 13일 수동 검토에서 미래 글로벌 공식 예고 1개와 근거가 제한적인 예상 기간 3개를 추가했습니다. [출시 로드맵](release-roadmap.md)에 비교 출처와 수집 한계를 기록합니다. 수동 실행은 예약 실행의 전체 흐름이 성공했다는 증거가 아닙니다. 공개된 예상 변경 이력을 보존하고 새 출처 검토 후에만 `forecasts.reviewedAt`을 갱신합니다. 모델은 이 작업의 설정을 따르며, 정기 점검 성공이 예측 정확도의 검증을 뜻하지 않습니다.
