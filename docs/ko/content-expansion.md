## 경쟁 사이트 확인

사용자가 제공한 [wwm-app 외관 도감](https://wwm-app.com/ko/ledger/codex)을 데스크톱에서 확인했습니다. 한 세션에서 목록 419개를 함께 렌더링했고, 작은 재화 아이콘을 포함한 이미지 요소 812개, 네이티브 영상 요소 0개, 광고·빈 프레임 등을 포함한 iframe 요소 12개를 관찰했습니다. 화면 구조를 확인한 수치이며 동시 다운로드 수나 통제된 성능 측정값이 아닙니다.

먹 속의 봄 항목은 목록과 상세에 [같은 움직이는 WebP](https://wwm-app.com/images/roadmap/2026/09/cosmetic.9.1.webp)를 사용합니다. 2,404,106바이트, 1280×720, 76프레임, 약 5.4초 길이의 무한 반복입니다. 지연 로딩은 다운로드를 미룰 뿐 움직이는 파일을 정지 이미지로 바꾸지는 않습니다. 이 대표 파일을 확인했으며 모든 이미지를 조사한 것은 아닙니다. 애니메이션 이미지 처리, 큰 목록, 광고가 부담에 기여할 수 있지만 CPU 추적으로 멈춤의 원인을 확정하지는 않았습니다.

폭넓은 분류와 획득 정보는 수집 범위를 정하는 참고가 됩니다. 연운경은 간단한 조작과 공식 출처가 뒷받침하는 정보를 유지하며 경쟁 데이터나 추정 명칭·날짜를 공식 사실로 옮기지 않습니다.

## 재생 방식과 용량 기준

- 목록은 단일 프레임 WebP입니다. 썸네일과 갤러리에 움직이는 파일이 들어오면 자동 검사가 실패합니다. 초기 목록은 최대 24개만 렌더링하고 필요한 경우에만 ‘더 보기’ 하나로 이어갑니다. 현재 18종에서는 버튼이 표시되지 않습니다.
- 이펙트 상세는 정지 이미지와 재생 버튼으로 시작합니다. 클릭하기 전에는 영상 재생기나 영상 주소를 화면에 넣지 않습니다. 외관 영상은 한 번에 하나만 활성화합니다. 영상 영역을 벗어나거나 탭을 숨기면 재생기를 제거하고, 돌아와도 자동 재생하지 않습니다. 제거 시 디코더와 진행 중 다운로드를 정리합니다.
- 기본 재생 조작, 모바일 화면 내 재생, 무음으로 시작, 반복 없음, 길이·용량 표시, 원본 링크를 제공합니다. 외부 임베드도 클릭한 뒤에만 불러오고 숨겨지면 제거합니다. `preload="none"`은 권고에 불과하므로 재생기의 조건부 생성으로 초기 로딩을 제한합니다. [MDN video](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/video)
- 102,489,850바이트, 2400×1080 원본을 **4,182,232바이트로 95.9% 축소**했습니다. 1280×576, 30fps, 29.034초, H.264/AAC이며 재생 정보가 영상 프레임보다 먼저 오도록 구성했습니다. 정지 미리보기는 56,478바이트입니다. 원본 대용량 영상과 경쟁 사이트 파일은 Git에 넣지 않습니다.
- 자동 제한: 썸네일 160KB, 전체 이미지 2.5MB, 영상 8MB·60초·1280×720 이하. 현재 썸네일 22개의 합계는 1,567,354바이트이며 첫 3개 이후는 지연 로딩합니다. 이 용량 전체를 첫 접속에 내려받는다는 뜻은 아닙니다. 초기 8종의 542KB 수치는 이전 상태입니다.

현재 영상의 재현 가능한 인코딩 설정은 가로 1280, H.264 `preset slow`, CRF 27, 최대 1050 kbit/s·버퍼 2100 kbit, AAC 80 kbit/s, `+faststart`입니다. 원본은 Git 밖에 보존하고 결과 파일의 실제 바이트를 기록합니다. 정지 이미지 자리에 움직이는 파일을 대체하지 않습니다.

## 검증

타입 검사, 도메인·미디어 검사 15개, 출처 참조, 양언어 번역, 용량 기록, MP4 초기 재생 정보 검사가 통과했습니다. 게시용 빌드에서 영어·한국어 분류와 언어 이동, 목록 18종의 정지 미디어, 320px·390px 가로 넘침 없음, 클릭 후 재생 시간 진행·반복 없음, 아래로 스크롤한 뒤 재생기 제거를 확인했습니다. 중국 캘린더에는 2026년 9월 신규 10종이 연결됩니다. 탭 숨김 시 정리는 구현했지만 별도 탭 전환 검증은 수행하지 않았습니다. 24개 렌더링 경계도 더 큰 실제 도감으로 부하 검증한 상태는 아닙니다. 실제 기기와 느린 통신 환경은 별도 측정 대상이며 경쟁 사이트보다 빠르다는 실측 주장은 하지 않습니다.

## 재생 시작 문제 수정

인앱 브라우저에서 게시된 이펙트를 시작하자마자 멈추는 현상을 재현했습니다. 재생기는 준비된 상태로 화면에 남아 있어 화면 밖 정리 동작이 원인은 아니었습니다. 같은 MP4를 사용하는 별도 로컬 페이지에서 React·가시성 정리 없이도 유음 자동 시작은 0.000초, 클릭 즉시 재생은 0.006초에 버퍼가 남은 채 멈췄습니다. 무음에서는 29.034초 끝까지 재생됐습니다. 동일한 H.264/AAC 파일 전체를 FFmpeg로 검사해 디코딩 오류가 없음을 확인했습니다.

네이티브 미리보기는 기존 재생 클릭 이후 무음으로 시작하도록 수정했습니다. 기본 볼륨 조작은 유지하며 강제 재개 반복·재생기 반복 생성·추가 영상 다운로드·재인코딩은 넣지 않았습니다. [MDN의 무음 시작 지침](https://developer.mozilla.org/en-US/docs/Web/Media/Guides/Autoplay#handling_autoplay_failure_with_media_controls)을 따릅니다. 확인한 차이는 해당 브라우저에서의 유음·무음 재생이며, 소리가 있을 때 정지시키는 정확한 브라우저·운영체제 내부 원인은 확정하지 않았습니다. 환경별 유음 재생은 인증하지 않습니다.

수정한 프로덕션 빌드를 인앱 브라우저에서 재생해 0.173초·22.446초 진행 후 29.034초에 `ended=true`로 종료됐음을 확인했습니다. 클릭 전에는 video 요소가 없었습니다. 타입·콘텐츠 검사, 기존 검사 18개와 프로덕션 빌드도 통과했습니다.

390px 화면에서 다시 재생해 29.034초에 `ended=true`로 끝났습니다. 재생기가 화면 밖으로 완전히 나가면 제거되고 재생 버튼이 복원됐으며 콘솔 경고·오류는 관찰되지 않았습니다. [PR #9](https://github.com/developdh/Winds-Ahead/pull/9)에 수정을 기록했고 앱 변경 커밋의 GitHub CI가 통과했습니다. 인앱 화면 크기 검증이며 실제 iOS·Android 기기 검증은 아닙니다.

2026년 9월 13일 11:50:32 UTC에 소유자 전용 접근 범위를 유지한 버전 5로 게시했습니다.

## 소리를 켠 뒤 멈추는 문제 조사

사용자는 소리를 켜면 영상이 다시 멈춘다고 알렸습니다. 무음 시작은 조용한 미리보기 동작이며, **이번 문제의 근본 해결책은 아닙니다.** 9월 13일 후속 검사에서 테스트 Mac의 Bluetooth 미디어 제어가 재생을 중단시키는 것을 확인했습니다.

- 동일한 29.034초 MP4가 인앱 브라우저와 일반 Google Chrome 모두에서 멈췄습니다. React·화면 밖 정리·사이트 코드를 제외한 로컬 페이지에서도 버퍼와 재생 준비 상태는 유지됐으며, 클릭 직후 `play()` 요청은 오류 없이 성공했습니다.
- 오디오를 44.1kHz AAC로 재인코딩하거나 모노로 바꾸고, 실제 소리만 PCM WAV·Opus로 재생해도 멈췄습니다. 실제 소리의 4초 구간은 유음으로 끝까지 재생됐지만, 별도로 만든 30초 테스트 소리는 같은 정지 명령을 받았습니다. 이 결과로 브라우저 전체에 적용되는 길이 기준을 확정하지는 않습니다.
- 임시 진단 페이지에서 Media Session의 정지 명령을 기록한 뒤 그대로 이행하는 처리기를 등록했습니다. `MEDIA SESSION PAUSE ACTION`이 확인됐으며, 그 외에는 페이지의 JavaScript 정지 추적에서 중단을 시작한 호출이 없었습니다.
- **12:03:35.105 UTC**에 macOS `mediaremoted`가 **`com.apple.bluetoothd`**에서 Google Chrome으로 보낸 `Pause` 명령을 기록했습니다. 12:03:35.219 UTC에 재생 상태가 Playing에서 Paused로 바뀌었습니다. 앞선 인앱 브라우저 재현에서도 같은 Bluetooth 정지 명령을 확인했습니다. 12:04:00.058 UTC에는 독립적인 긴 테스트 소리에도 Bluetooth 정지 명령이 전달됐습니다.

사용자 승인을 받아 연결된 Bluetooth 헤드셋만 잠시 해제했습니다. macOS에서 내장 MacBook Pro 스피커가 선택되고 출력 음소거가 꺼져 있음을 확인했습니다. 영상과 사이트 코드를 바꾸지 않은 상태에서, 격리 페이지의 동일 영상이 처음부터 유음으로 재생돼 **29.034초**에 `ended=true`로 끝났으며 Media Session 정지 명령은 없었습니다. 게시된 버전 5 상세 페이지에서도 약 8.5초에 기본 볼륨 조작으로 소리를 켠 뒤 29.034초까지 이어졌고, `muted=false`·미디어 오류 없음·`ended=true`를 확인했습니다.

직접적인 원인은 유음 재생 직후 Bluetooth 헤드셋 연결을 통해 전달된 정지 명령이며, 해당 환경에서는 연결을 해제하자 중단이 사라졌습니다. 착용 감지 등 헤드셋의 어떤 동작이 명령을 만드는지는 아직 확인하지 않았습니다. 테스트 Mac과 내장 스피커에서 유음 완주를 확인한 결과이며 실제 모바일 기기나 다른 오디오 액세서리 전체에 대한 인증은 아닙니다.

사이트에 강제 재개 반복이나 시스템 정지 명령을 무시하는 처리는 추가하지 않았습니다. 그렇게 바꾸면 사용자가 의도한 헤드셋 정지 조작도 무시하게 됩니다. 진단용 미디어 파생본, 원시 시스템 로그, 기기 주소·식별자는 Git에 넣지 않았습니다. 원본 미디어와 게시 사이트는 그대로이며 이번 검증 기록 갱신에는 새 배포가 필요하지 않습니다.
