# 릴리스 발행

[English](../en/releasing.md) · [최신 릴리스](https://github.com/developdh/Winds-Ahead/releases/latest)

사용자는 **첫 GitHub 릴리스를 v0.1.0으로 만들고, 이후 업데이트를 완료할 때마다 릴리스를 발행**하도록 요청했습니다. 기능·오류 수정·조사 자료·번역·문서 변경에 모두 적용합니다. 관련 커밋은 완성된 업데이트 하나로 묶습니다. 변경 없는 출처 점검, 진행 중인 작업, 초안 PR에는 릴리스를 만들지 않습니다.

## 버전 기준

| 변경 | 예시 |
| --- | --- |
| 오류 수정, 정보·사진·캘린더 갱신, 번역·문서 변경 | `0.1.0` → `0.1.1` |
| 의미 있는 새 기능 | `0.1.x` → `0.2.0` |
| 안정 버전 1.0 전환 또는 이전 작업이 필요한 변경 | 별도로 판단하고 호환성 영향을 노트에 설명 |

Git 태그에는 `vX.Y.Z`, `site/package.json`과 `site/package-lock.json`의 최상위·루트 패키지 버전에는 `X.Y.Z`를 사용합니다. 기존 태그와 릴리스를 확인하고 다음 버전을 정합니다. 발행한 태그를 다른 커밋으로 옮기지 않습니다. 수정이 필요하면 새 패치 릴리스를 냅니다.

## 업데이트 완료 절차

1. 검토 가능한 브랜치에서 변경을 마무리합니다. 작업 폴더에는 의도한 변경만 남기고 PR의 영어·한국어 변경과 출처를 확인합니다.
2. `site/`에서 `npm version patch --no-git-tag-version`으로 버전과 잠금 파일을 함께 올립니다. 기능 릴리스는 `minor`를 사용합니다. 최초 릴리스는 이미 `0.1.0`입니다. npm에 배포하는 작업이 아니며 앱의 npm 패키지는 비공개 설정을 유지합니다.
3. `docs/en/releases/X.Y.Z.md`, `docs/ko/releases/X.Y.Z.md`에 대응하는 노트를 추가합니다. 최종 동작, 관련 수정, 실제 검증과 중요한 한계를 적고 웹사이트·관련 PR 링크를 포함합니다. 이전 노트는 보존합니다.
4. 변경에 맞는 검증을 수행하고 릴리스 커밋의 프로젝트 CI 성공을 확인합니다. 앱·콘텐츠 변경은 타입·테스트·콘텐츠·운영 빌드를 검증합니다. 관련 UI는 한영·모바일에서 확인합니다. 문서 변경은 버전·링크·내용을 검토하며 하지 않은 브라우저 검증을 적지 않습니다.
5. 검토한 변경을 `main`에 반영하고 정확한 커밋을 확인합니다. GitHub 자동 병합은 활성화하지 않습니다. 병합이나 필수 검증이 막히면 준비한 작업을 보존하고 상황을 알리며, 릴리스 완료로 보고하지 않습니다.
6. 검증한 커밋에 주석 있는 `vX.Y.Z` 태그를 만들어 푸시합니다. 기존 태그로 초안이 아닌 GitHub 릴리스를 발행합니다. 제목은 `Winds Ahead v0.1.0`처럼 영어로, 본문은 영어·한국어를 함께 적습니다. 명시적인 시험판이 아니면 최신 릴리스로 지정합니다. `gh release create`에 `--verify-tag`, `--notes-file`을 사용해 의도하지 않은 태그 생성을 방지합니다.
7. 공개된 릴리스 주소, 태그 커밋, 버전, 노트와 최신 상태를 확인하고 사용자에게 릴리스 링크를 전달합니다.

GitHub 릴리스와 웹사이트 배포는 별도 결과입니다. 사이트 변경은 기존 Sites 절차로 배포하고 실제 주소를 확인합니다. 배포가 대기 중이거나 실패했다면 그 상태를 명확히 적습니다. 문서만 바꾸면 사이트를 다시 빌드할 필요가 없습니다. GitHub가 태그별 소스 압축 파일을 제공하므로 비밀키·조사 원본 다운로드·미검토 미디어 묶음을 추가 첨부하지 않습니다.

기존 캘린더 작업의 갱신을 포함해 매번 업데이트를 마무리하는 절차입니다. 별도 예약 작업을 추가하거나 자동 병합을 켜지 않습니다. 발행이 실패하면 태그·릴리스가 이미 생성됐는지 먼저 확인해 중복을 방지합니다.
