# 개발·운영 계획 v0.2

[English](../en/delivery-plan.md) · [제품 기획](product-plan.md)

## 1. 이번 단계와 결정 상태

현재 산출물은 기획 문서, 출처 조사, GitHub 협업 기반입니다. 화면 구현이나 사이트 배포는 아직 진행하지 않습니다.

| 상태 | 내용 |
| --- | --- |
| 사용자 확정 | Winds Ahead / 연운경(燕雲鏡), 중국 서버 외관 기반 정보·사진·영상, 글로벌 예상 캘린더 |
| 사용자 확정 | 사이트·문서 영어/한국어, PR 영어, 진행 중 GitHub 업데이트 |
| 사용자 확정 | 새 비공개 GitHub 저장소로 시작 |
| 사용자 확정 | GitHub 방식 콘텐츠 운영, 초기 AI 갱신은 이 작업의 정기 점검 |
| 사용자 확정 | 개발 기간보다 디자인·UI/UX·반응형·속도의 완성도 우선 |
| 제안 기본값 | 탐색 중심 첫 화면, 로그인 없는 관심 저장, 수동 검증 콘텐츠 운영, 먹빛·청옥 시각 방향 |
| 구현 전 확인 | 대표 외관 자료와 미디어 이용 근거, 실제 서버별 날짜/명칭 연결, 호스팅 실행 경로 |
| 공개 전 결정 | 도메인, 운영 연락·공개 제보 경로, 공개 범위, 필요 시 분석 도구 |

미결정 항목 중 구현과 무관한 선택 때문에 앞 단계 작업을 멈추지 않습니다. 실제 비용이나 외부 연락이 필요한 선택은 구체적인 결과와 조건을 제시한 뒤 처리합니다.

## 2. 제안 기술 방향

초기에는 **React·TypeScript 기반의 검색 가능한 페이지와 저장소에서 관리하는 구조화된 콘텐츠**를 권장합니다. 외관 ID, 미디어 참조, 서버별 기록, 번역을 나누어 저장하고 배포 전 스키마 검증을 수행합니다. 읽기 중심 페이지는 가능하면 미리 생성하며, 필터·캘린더·관심 저장만 필요한 상호작용을 추가합니다.

구현 시작 시 당시의 Sites 지원 스타터와 호스팅 호환성을 확인해 구체 프레임워크와 버전을 정합니다. 이번 단계에서는 설치·호스팅 등록·외부 서비스 구매를 하지 않습니다. 소스의 기준은 사용자가 요청한 GitHub 저장소로 유지하고, 추후 호스팅용 저장소가 따로 필요하면 배포 연결만 기록합니다.

미디어 본체는 허용된 외부 플레이어 또는 이미지 저장소/CDN을 사용하고, Git에는 메타데이터·작은 코드 자산을 둡니다. 초기에는 선택된 GitHub 편집 방식을 사용하며 독자 계정·운영 DB·별도 관리자 로그인은 필수 요소가 아닙니다. CMS는 추후 운영 방식을 재검토할 때의 선택지입니다. AI 판단은 방문자 요청 밖에서 수행합니다. [정기 점검과 캘린더 갱신](calendar-automation.md)

## 3. 단계별 범위와 완료 기준

작업 규모는 순서와 범위를 판단하기 위한 제안입니다. 달력 날짜나 개발 기간을 확정한 것은 아닙니다.

M1에는 실제 자료 기반의 세 핵심 화면 디자인과 클릭 가능한 프로토타입을 추가합니다. M2·M3는 화면 구현과 함께 반응형·접근성·속도를 검증합니다. 사용자가 요청한 품질을 위해 필요한 디자인 수정과 성능 개선을 단계 내에서 수행하며, M4는 전체 동선의 통합 검증에 사용합니다. [완료 증거와 성능 목표](design-quality.md)

| 단계 | 산출물 | 완료 기준 | 예시 영어 PR 제목 |
| --- | --- | --- | --- |
| M0 · 기획 | 양언어 PRD, 콘텐츠 정책, 출처 목록, 협업 규칙 | 두 언어 범위 일치, 실제 조사와 제안 구분, 저장소에 리뷰 가능한 변경 | `docs: define bilingual product and editorial plan` |
| M1 · 데이터·화면 검증 | 대표 5~8개 기록 초안, 공식 명칭 연결, 탐색/상세/캘린더 와이어프레임 | 원문과 미디어 사용 근거 확인; 확정/예상/미정/복각 사례의 화면 규칙 확인 | `feat: establish cosmetic data and core page layouts` |
| M2 · 도감 | 영어·한국어 경로, 검색/필터, 상세 갤러리, 소스 표시 | 대표 자료로 모바일·데스크톱 탐색과 재생; 필터 공유·언어 전환 유지 | `feat: add bilingual cosmetic catalog and media details` |
| M3 · 일정·관심 | 캘린더, 일정 미정 목록, 관심 저장, 변경 이력 | 날짜 정밀도/시간대/예상 만료 처리; 저장 차단 시 정상 탐색 | `feat: add release calendar and local watchlist` |
| M4 · 공개 준비 | 시드 확장, 정정 경로, 접근성·성능 확인, 미리보기·배포 | 핵심 사용자 동선 통과, 공개 데이터 품질 충족, 실제 연락 경로와 배포 복구 방법 확보 | `feat: prepare Winds Ahead for initial release` |
| M5 · 운영 개선 | ICS, 비교, 필요 시 CMS·계정·알림 | 실제 이용과 편집 부담에 따라 개별 범위 선정 | 기능별 PR |

M1에서 실제 예상 근거가 부족하면 합성 사례를 **테스트·와이어프레임 전용**으로 분리하고 공개 데이터에 포함하지 않습니다. 예상 날짜를 만들기 위해 최초 공개를 왜곡하지 않습니다.

## 4. 초기 공개 완료 기준

- 외관 카드에서 상세로 이동해 사진·영상·출처·CN/Global 상태를 확인할 수 있습니다.
- 대표 검색어가 세 언어의 이름/별칭으로 같은 외관을 찾습니다. 한국어·영어 UI 모두 필터 및 결과 수가 맞습니다.
- 번역이 없으면 준비 중 표시와 원명을 제공하고, 공식명과 임시 번역이 구별됩니다.
- 날짜·출시 상태·획득 정보의 근거와 확인일이 공개 기록마다 연결됩니다.
- 공식 이벤트와 예상이 상세·캘린더·변경 이력에서 일관되게 구분됩니다. 근거가 부족한 항목은 일정 미정입니다.
- 최소한 의상·헤어·무기·장신구와 여러 획득 방식의 대표 자료를 검증합니다. 목표 20~30개보다 완성도를 우선합니다.
- 모바일 360px, 태블릿, 데스크톱과 키보드·200% 확대에서 주요 동선이 막히지 않습니다.
- 영상 불러오기 실패, 이미지 없음, 빈 검색, 사라진 항목, 저장소 차단에 실제 대안·안내가 있습니다.
- 언어별 제목·설명·canonical·hreflang과 사이트맵을 검증합니다. 번역 URL이 중복 페이지로 혼동되지 않게 합니다.
- 사이트 안내에 비공식 팬 프로젝트 표시, 미디어 출처, 실제 오류·삭제 요청 경로가 있습니다.
- 주요 화면의 양언어·모바일/데스크톱 시각 검토와 느린 환경의 성능 측정 결과가 있습니다. 측정 조건과 실사용 데이터의 유무를 구분합니다.

## 5. 검증 계획

기획 단계는 문서 링크·양언어 범위·용어 일치를 검토합니다. 구현 전 애플리케이션 테스트를 추가하지 않습니다.

구현 단계에서는 날짜 변환·예상 범위·상태 전환·번역 누락·출처 연결처럼 틀리면 정보가 왜곡되는 부분을 자동 검증합니다. 브라우저 검증은 ‘검색 → 상세 → 관심 저장’, ‘언어 전환 후 같은 화면 유지’, ‘공식/예상/미정 확인’의 핵심 흐름을 중심으로 합니다. 모든 텍스트나 단순 스타일을 위한 중복 테스트는 만들지 않습니다.

시드 데이터 검증은 ID 중복, 참조 누락, 필수 번역, 근거 없는 날짜/가격, 사용 불가 미디어, 공개 상태와 편집 초안 혼입을 확인합니다. 성능은 실제 이미지와 영상 공급자를 붙인 후 측정합니다.

## 6. GitHub 운영

- 저장소: [developdh/Winds-Ahead](https://github.com/developdh/Winds-Ahead), 비공개. 현재 인증 계정에 생성하고 연결을 확인했습니다.
- `main`은 통합 기준입니다. `docs/...`, `feat/...`, `fix/...`, `content/...` 브랜치에서 의미 있는 작업 단위로 커밋합니다.
- PR 제목·본문·커밋 메시지는 영어를 기본으로 합니다. PR에는 변경 이유·결과·검증·남은 제한을 기록합니다.
- 사이트 콘텐츠와 문서의 의미를 바꾸는 PR은 한국어·영어를 함께 수정합니다. 사실 데이터는 공통 원본을 둡니다.
- 기획 초안은 draft PR로 공유하고, 완료된 구현은 검증 근거를 첨부합니다. 자동 병합을 이 규칙만으로 설정하지 않습니다.
- 기획 완료, 핵심 화면 완료, 일정 기능 완료, 공개 준비처럼 의미 있는 지점에 push/PR을 갱신합니다. 단순 로컬 수정마다 원격 기록을 만들지는 않습니다.
- 콘텐츠 갱신은 `content:` 커밋으로 출처와 변경 이유를 추적합니다. 코드·미디어·원문 저작권을 분리하고 외부 미디어를 프로젝트 코드 라이선스에 포함시키지 않습니다.
- 인증·네트워크 문제가 발생하면 로컬 결과를 보존하고 실제 원격 반영 여부를 명시합니다. 비밀키는 커밋하거나 출력하지 않습니다.

## 7. 작업 시작 순서

기획을 바탕으로 대표 외관과 출처를 선정한 뒤 세 핵심 화면을 구체화합니다. 이어서 데이터 검증과 양언어 구조를 만들고, 도감 → 캘린더·관심 목록 → 공개 준비 순으로 진행합니다. 배포와 계정·알림 확대는 해당 단계의 실제 요구에 맞춰 결정합니다.
